# Inference experiments from the literature

## Can a small cache make Flash-Next's disk-backed embedding faster?

The one-Spark Qwen3.8 Flash-Next FP4-Local recipe reads an n-gram embedding table from NVMe. Each generated token determines which rows the model needs. A cache that retains frequently reused rows across decoding steps could avoid some reads while leaving room for the model in shared memory. [One-Spark configuration](recipes/qwen38-flash-next-fp4-local.json) · [Checkpoint configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

Huang and Liu tested this idea on DeepSeek-V4.1-Flash with four H200s. The first lookup table had only 0.3 ms to fetch its rows before the model needed them. A later table had 9.3 ms. Reuse depended on the sessions being served. Flash-Next also looks up rows early, but its row format, memory bandwidth and SSD differ. The public B12X reader stages a batch of rows. Check the installed image for any additional caching before implementing a new one. [Paper, sections 4–6](https://arxiv.org/html/2611.13413v1) · [B12X disk row implementation](https://github.com/flashinfer-ai/flashinfer/blob/601cb12713fd73f1744b15fdea6f9ddaaf2b4ec3/flashinfer/experimental/b12x/sequence/_shared/disk_table.py)

The paper also measured Qwen Flash-Next itself. At 128 sessions on H200, its layer-one prefetch window was 0.27 ms. With a one-million-row cache and four disks, the cache served 93% of agent lookups and 57% of chat lookups. The proposed Spark test uses one NVMe drive, packed FP4 rows, one or four clients and a much smaller cache. [Qwen workload and Qwen results](https://arxiv.org/html/2611.13413v1#S6.SS7)

**Offline check, November 19, 2026.** Twelve archived single-client answers came from the two-Spark mixed-precision checkpoint. Each prompt asked for an orchard field guide with a different case number. Both checkpoints publish the same tokenizer. In archive order, 585 of 1,139 two-token windows (51.4%) and 443 of 1,127 three-token windows (39.3%) had appeared earlier. Counting only earlier windows in the same answer gave 110 (9.7%) and 51 (4.5%), respectively. The template makes this a deliberately favorable workload. Row IDs, device reads and latency require a live measurement. [Archived answers](results/qwen38-flash-next-2026-11-19/kv2g-c4/requests.jsonl.gz) · [Tokenizer](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/tokenizer.json)

To reproduce the count, select `concurrency == 1` in the archive and preserve row order. Encode each `answer` with the pinned tokenizer using `add_special_tokens=False`. Slide a window of two or three tokens by one token at a time within each answer. Count each window already seen before inserting it. For the within-answer count, start with an empty set at each answer. Retokenization yielded 1,151 visible tokens versus 1,152 reported by the server. The count excludes prompts, crosses no answer boundaries and assumes no eviction.

**Measured on GB10.** Enabling a 64 MiB exact row cache reduced physical reads by 91% on single-client edits, with 49.90 vs 49.58 output tok/s for stock. All 135,088 verified gathered rows matched byte for byte. [Live cache comparison](results/qwen38-flash-next-ple-2026-11-19/#live-cache-comparison) A cold 64 MiB cache simulation hit 91% of distinct row lookups on repeated one-client edits and 24% on unrelated one-client prose. The native direct-I/O reader issued 218 MB and 325 MB of reads in those two runs. [Device counters, byte comparisons and raw four-workload traces](results/qwen38-flash-next-ple-2026-11-19/)

**Hardware protocol.** Trace the actual PLE row IDs on repeated editing sessions and on unrelated prompts. Sum the reader's per-call `read_bytes` and `unique_blocks` and record NVMe device reads separately. Replay the trace with exact packed rows and their scales under 0, 64 and 256 MiB budgets. If a bounded cache removes physical I/O on the critical path, compare stock and cached serving at one and four clients. Keep MTP and KV settings fixed, prevent cross-request prefix-KV hits, and check gathered bytes, inter-token latency, first-token latency, memory and GPU joules per output token. A drop in read count with flat or worse latency is a result worth recording. [Native per-call reader counters](https://github.com/flashinfer-ai/flashinfer/blob/601cb12713fd73f1744b15fdea6f9ddaaf2b4ec3/flashinfer/experimental/b12x/loader/_ple_reader.c)

## Can Qwen speed up repeated code edits without a separate draft model?

SuffixDecoding proposes continuations from token sequences in a prompt and earlier outputs. The target model verifies the proposals, so the method needs no draft checkpoint. The authors report a mean 2.5× speedup over vanilla decoding in their SWE-Bench comparison. vLLM 0.33.0 supports the method with the optional `arctic-inference==0.1.1` package. Its `suffix_decoding_max_cached_requests=0` setting keeps current-request matching and disables the shared history. [Authors' results](https://suffix-decoding.github.io/) · [Pinned vLLM configuration](https://github.com/vllm-project/vllm/blob/v0.33.0/vllm/config/speculative.py)

**Measured on GB10.** Suffix drafting without shared history produced the same token IDs as ordinary decoding on all edits at one and four clients and accelerated them by 4.20× and 3.48×. Adding a history of up to 32 requests slowed edits and improved single-client prose throughput. [Results of all four draft policies](results/qwen38-27b-drafting-2026-11-19/)

**Hardware controls.** With built-in n-gram drafting the lab measured 3.93× ordinary throughput for one client on exact code edits and 3.4% less throughput on unrelated prose. [Measured controls](results/qwen38-27b-drafting-2026-11-19/) Use the one-Spark Qwen3.8-27B baseline. Run the same proposed code edits and unrelated prose through ordinary decoding, built-in n-gram drafting, and suffix drafting. Compare current-request matching with a bounded history populated by earlier distinct edits. Use the same prompt prefix-cache policy, reset history between workloads, and measure one and four clients. Record proposed and accepted tokens, end-to-end latency, output tokens per second, GPU energy and whether the generated edits pass their tests. The benchmark records where the extra accepted tokens repay verification and scheduling costs on GB10. [Lab baseline](results/qwen38-27b-scaling-2026-11-19/) · [vLLM 0.33.0 suffix decoding](https://docs.vllm.ai/en/v0.33.0/features/speculative_decoding/suffix/)
