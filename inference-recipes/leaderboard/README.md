# Open-weight inference queue

The November 19, 2026 snapshot contains 44 releases with a current Artificial Analysis Intelligence Index score. The queue retains the highest-scoring effort setting per release and sorts by its unrounded score. A November 20 refresh reproduced the same release order and displayed scores. A leaderboard result belongs to the provider configuration named in the row. The Spark experiments use their own prompts, reasoning settings and metrics. The [checkpoint inventory](weights-2026-11-19.csv) covers all 44 ranked releases. Each row links an immutable Hub revision. Sizes sum the root SafeTensors files, including auxiliary or draft files in the root. The count omits duplicate consolidated copies where the conventional weight files are also present. Model variants such as Xiaomi's RL and MOPD are listed separately because the leaderboard label alone does not identify the locally downloaded variant.

The planning column picks the smallest of one, two or four Sparks allowing 110 GiB per node for weight files. Each lab Spark reports about 121 GiB total. The allowance is a consistent way to triage downloads. An engine may repack, replicate or offload tensors, and individual ranks may have different memory demands. Runtime support, KV cache, working memory, interconnect and a successful completion determine actual serving fit. Ranks 2, 3 and 8 have published serving configurations whose checkpoint layout or compression changes the required hardware.

The November 20 GGUF inventory verifies the architecture string in each first-shard header and sums the complete text model’s individual shard sizes at a pinned revision. It excludes optional vision, audio and draft heads. Each row carries its candidate node count and source manifest. [GGUF inventory](gguf-2026-11-20.csv)

On one Spark the lab built llama.cpp at `6aee50801d091f78b3baacd505f5e95d8e8f6838` for ARM64 and SM121a. We fetched the beginning of every shard over HTTP ranges, extended each staged file sparsely to its manifest size, and checked that its entire GGUF header was present. The allocation-free model load then checked named tensor shapes across all shards. Eleven conversions passed, including three MiniMax-M3 and three Beam variants, and two original Inkling conversions reached an unsupported architecture. The same two Inkling files passed with the model-specific branch. These checks cover metadata only. GPU allocation, decoding and answer quality require the actual weights. [Per-conversion results](gguf-loader-2026-11-20.csv) · [Probe source](gguf_loader_probe.cpp) · [Engine revision](https://github.com/ggml-org/llama.cpp/tree/6aee50801d091f78b3baacd505f5e95d8e8f6838)

To repeat against a local shared-library build, compile the probe with `c++ -std=c++17 -I "$src/include" -I "$src/ggml/include" gguf_loader_probe.cpp -L "$lib" -lllama -lggml -lggml-base -o probe`. Set `LD_LIBRARY_PATH` to include the build's library directory. Run `./probe header SHARD PREFIX_BYTES` for each staged shard, then `./probe model FIRST_SHARD`. The lab fetched up to 16 MiB of each first or standalone file and 256 KiB of each subsequent shard. Retain the original shard names together in one directory.

On a GB10 we used llama.cpp’s allocation-free context initialization to plan five quantized checkpoints. For four 8K slots, changing the layer split reduced the largest projected allocation for DeepSeek V4 Pro 0813 IQ1_M from 98.60 to 91.96 GiB. For the two-rank Muse IQ1_M it fell from 104.74 to 101.77 GiB. The table includes model, context and compute buffers, with host buffers charged to the head. We summed bytes per transformer block, charged input embeddings to the head, and used the remaining non-block weights as an initial estimate for the final block. Among contiguous cuts we selected the one minimizing the largest estimated weight allocation. The engine then supplied the buffer counts in the table. All runs used 512 batch tokens, microbatch 256, a unified FP16 KV cache, and one physical GB10 with one or three loopback CUDA RPC workers. We previously cross-checked loopback against four physical Sparks for Inkling. Token generation and application accuracy on these five checkpoints remain to be tested.
